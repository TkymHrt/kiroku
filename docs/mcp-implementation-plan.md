# 日記MCP・日次要約 実装計画書

2026-10-20。実装エージェントへの依頼用。判断の背景は[mcp-feasibility.md](mcp-feasibility.md)を参照。

## 目的・方針

きろくの日記をChatGPTから一覧・検索・取得でき、毎日00:15 JSTに前日分を要約して保存できるようにする。既契約のChatGPTとWorkers/D1無料枠を使い、追加費用なし・まず1年の運用を目指す。

構成は **ChatGPT定期タスク → Cloudflare認証付きMCP → 既存D1**。Slack Dumperでは接続・定期取得に成功済みなので、その可否の再調査より、日記固有の実装と無人書込の検証に集中する。ホスト先は`https://mcp-slack.nutfes.net/mcp`。認証の具体方式は未確認のためManaged OAuthと決めつけない。既存設定が参照できない場合は、Managed OAuth等の無料候補で検証を進め、未確認部分を明記する。

本計画はMVP後の追加機能として扱い、実装時に`docs/requirements.md`等の対象範囲を更新する。

## 初期範囲

| ツール                   | 機能                                                                            |
| ------------------------ | ------------------------------------------------------------------------------- |
| `list_diaries`           | 日付範囲・cursorで一覧と要約の有無・鮮度を返す                                  |
| `get_diary`              | 原文、既存要約、ID・version・epochを取得。長文は同じ版で分割                    |
| `search_diaries`         | 日本語の部分一致＋日付絞り込み。短い該当箇所を返す                              |
| `list_pending_summaries` | 前日までの未要約・更新後の日記を少数件返す。対象日はサーバーでTokyo日付から計算 |
| `save_summary`           | 元本文の版と要約revisionを照合して要約だけを保存・更新                          |

読取4ツールは`readOnlyHint: true`、`save_summary`は書込として宣言する。FTS・embedding、原文のAI編集、任意SQL、要約用UI、Cron/Workers AI、セルフホスト、自動バックアップは初期範囲に含めない。

## 守る条件

- `AGENTS.md`と関連文書、インストール済みVoidのドキュメントに従う。Bun/mise・Void CLIを使用し、生成物を直接編集しない。
- 既存の本人限定Access・Worker側JWT照合・ブラウザAPIのCSRF保護を維持する。MCP入口に限定した認証・Origin/Host検証を設計し、匿名・別人・期限切れ・設定不足を拒否する。Slack用の秘密情報は流用しない。
- 要約は本文と別管理し、本文versionを進めない。保存時にdiary ID・source version・DB epoch・要約revisionをprimary優先で照合する。ゴミ箱は検索・要約対象外、完全削除では要約履歴も削除する。
- 要約用の操作ID・payloadを送信前に固定し、同ID同内容の再送は重複適用しない。receiptと要約変更を同一batchで保存する。既存本文用receipt・absenceToken・epochの契約と無期限保持を変更しない。
- 本文分割中の更新を検知し、切り詰めた本文を全文として要約しない。端末だけの未同期下書きは対象外とする。本文・検索語・認証情報をURLやログに含めない。
- 件数・返却バイト数・検索回数・再試行に上限を設ける。通常の保存を圧迫する全件取得ループを防ぎ、日記本文中の命令や外部URLを実行指示として扱わない。

## 実装順序

1. **読取MCP**：小さいstateless Streamable HTTP入口と共通サービスを実装。既存の日記APIを参考に、一覧・取得・部分一致検索を追加する。ゴミ箱除外、分割、取得上限をローカルで確認する。
2. **認証と無料枠の確認**：既存MCPのCloudflare認証方式を参照し、きろく専用の本人限定認証へ適用する。Managed OAuthは適合する場合の候補。MCP Inspector・架空データで接続を確認し、実Workersで認証込みCPUとD1読書量を測る。CPU 10ms枠で安定しない場合は最適化し、無料運用の可否を報告する。
3. **要約の保存**：別表・要約revision・再送用receipt・要約履歴を設計し、Voidでmigration生成・レビュー。本文更新後は古い要約を未処理へ戻し、削除・復旧との整合性を保つ。バックアップ復元処理とJSON出力仕様を新データ構造に合わせて更新する。
4. **日次処理**：プラグイン接続手順と登録用プロンプトを用意。00:15 JSTに前日分を日本語200〜400字程度で要約し、未記載の事実を補わず保存する。失敗・遅い同期・追記は次回回収し、同じ版の再生成を避ける。手動実行後、定期実行で書込承認・再送・回収を確認する。
5. **運用文書**：要件・設計・認証・復旧・検証記録を更新する。容量250MB、または半年以内に500MB到達見込みを移行検討の目安とする。公開は既存の手動運用に従い、実証済みと未実証を区別して引き渡す。

## 受入条件・検証

- 一覧・日本語の短語検索・原文取得が動作し、取得上限とゴミ箱除外が有効。匿名等を拒否し、既存画面・同期・CSRF保護に回帰がない。
- 要約生成中の本文変更、古い要約revision、削除、同日再作成、epoch変更を拒否。同一操作の再送は一度だけ適用され、並行書込でも本文を壊さない。
- 深夜の対象日・年境界、空の日、長文分割中の更新、要約後の追記、失敗翌日の回収を確認。実ChatGPTで定期実行から要約保存まで成功する。
- 本番データを使わず検証し、実クラウド試験が必要なら一時的な架空データ用リソースだけを使う。有料プランや追加API課金を有効にしない。

```powershell
mise exec -- bun run check
mise exec -- python scripts/backup_restore.py self-test --report test-results/local-backup-proof.json
```

加えてMCPのプロトコル・認証・同時実行・再送を検証する。既存E2EはAGENTS.md指定の安全なローカル環境で、画面や同期に変更がある場合に実行する。既存の`mcp-feasibility.mjs`と`mcp-capacity.py`は参考実験であり、本実装の合格証明には代用しない。

成果物：実装、migration、必要なテスト、更新した関連文書、ChatGPT接続・定期タスク登録手順、CPU/容量/読書量と未完了項目の短い報告。
