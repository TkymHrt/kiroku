# 通信制限下の性能調査（2026-10-30）

以下は `df2bad5` 時点の実装前の調査記録。承認後の実装と公開結果は [検証範囲](verification.md) と [公開記録](deployment.md) に記録する。

機能・デザインを保ったまま改善できる余地を確認した。効果をブラウザで比較できたのは、ハッシュ付きJS/CSSの再利用と、メモ編集中の非表示一覧の計算抑制。対象はmainの `df2bad5`。本番コード・設定・DBは変更しておらず、試作品は端末の `test-results/` に隔離した。

[計測値と検証範囲](performance-audit-proof.json)に結果を保存した。本番で行ったのはHTML・JS・CSSへの認証付きHEADだけで、日記・メモ・session・export APIの取得や書込は行っていない。

## 読み込みの比較

本番ビルドをloopbackの静的サーバーから配信し、APIは架空の応答だけに置き換えた。Edge headless、390px幅、CDPで上下128/256kbps・latency 400ms・CPU処理速度4分の1に設定。gzip転送で条件を揃えた。数値はページ移動開始から一覧取得完了までで、IdPのログインや実D1の処理時間は含まない。

| 回線    | 場面           | 現状相当 | JS/CSS再利用候補 |
| ------- | -------------- | -------: | ---------------: |
| 128kbps | 初回           |  22.85秒 |          22.92秒 |
| 128kbps | 同一版への再訪 |  22.54秒 |           1.76秒 |
| 256kbps | 初回           |  12.55秒 |          12.64秒 |
| 256kbps | 同一版への再訪 |  12.28秒 |           1.58秒 |

128kbpsは各条件2回の中央値、256kbpsは各1回の参考値。再訪は同じブラウザ環境での通常のページ移動で、強制再読み込みではない。再利用時のJS/CSSのサーバー取得は2件から0件になり、325,849 bytesのgzip本文の再転送が不要になった。日記を開く・端末編集・一覧へ戻る操作も実行し、全12回のページ表示でJavaScript例外はなかった。初回は同じ量のコードを取得するため改善しない。

本番HEADではHTML・JS・CSSすべてに `Cache-Control: no-store` と `Pragma: no-cache` があり、`Content-Encoding: br` も確認した。本番ではすでにBrotli圧縮されている。上表は再現条件を揃えたgzipの模擬試験であり、本番やAndroid実機でそのまま同じ秒数になるとは扱わない。

実装箇所は `public/_headers`、`middleware/01.security.ts`、`server/security.ts` とVoidの静的fallbackの境界。内容ハッシュが検証できるJS/CSSだけに限定し、HTML・API・エラーを誤って長期保存しないことをWorkers連携と本番ヘッダーで確認する必要がある。認証の省略や本文キャッシュの追加は不要。

Cloudflareはハッシュ付き静的資産のブラウザキャッシュをサポートしている。一方、複数の `_headers` ルールの同名ヘッダーは結合され、Workerが生成する応答には別の扱いが必要なため、汎用ルールに追記するだけで完了とはしない。[公式仕様](https://developers.cloudflare.com/workers/static-assets/headers/)

## メモ入力の比較

`src/components/NotesWorkspace.tsx:326` の `items` は、メモを開いている時も保存通知のtickで無効になり、対象の端末下書きを走査する。`summarizeNote()` はチェック数と抜粋のためにMarkdownを解析する。サーバー一覧に同じ版があるメモは省略されるが、未同期・端末のみ・現在のサーバーページにないメモは再計算される。

試作品では、メモ選択中はこの計算を省き、一覧へ戻った時に最新状態から計算した。製品ソースを編集せず、ビルド中の変換だけで比較した。

100件の保存済み架空メモ、各10KB、サーバー一覧は空、390px幅・CPU4倍減速のEdgeで、現状→候補→候補→現状の順に独立した4環境を実行した。起動時の送信が0件であることを確認し、1件を開いて各5文字入力した。

| 指標                                                 |    現状 | 非表示一覧の計算抑制 |
| ---------------------------------------------------- | ------: | -------------------: |
| キー入力から2回目のrequestAnimationFrameまでの中央値 | 384.4ms |               22.9ms |
| P95                                                  | 454.5ms |               42.9ms |
| 入力区間の長時間処理                                 |    18回 |                  0回 |

各候補10キーの比較で、応答指標は約94%短縮した。入力した5文字が本文末尾に保持され、戻った一覧100件のタイトル・順序・チェック数・抜粋が一致し、CSSも同一だった。本文全体の一致はこの比較では検査していない。JavaScript例外・想定外のAPI通信は0件。保存応答は試験用に保留し、ネットワーク完了のばらつきを除いた。

この指標はブラウザの描画スケジュールを利用した応答性の代理指標で、実際のinput-to-paintやINPの測定ではない。100件×10KBという条件での因果関係を確認した結果であり、メモ数が少ない場合の効果やAndroid実機の速度は別途確認する。

## 同期と配信物の追加調査

未同期10件を復元すると、日付ごとのキューが独立してPOSTを同時開始した。各本文が約1MBなら、128kbpsで上りだけでも合計約631秒分の帯域が必要になる。現在の1要求180秒の期限に対して、複数の大きな送信が競合すると期限切れと再送を招く可能性がある。小さい変更を待たせすぎない公平な順番と、大きい本文の同時送信数の制御が候補になる。これは実コードの要求数とサイズからの推定で、実回線で10件すべてが失敗したという実証ではない。

同じ日記の未変更時の全文GETと、保存成功時の全文応答にも転送量を減らす余地がある。約1MBの架空日本語GETはgzipで約116KB、反復の少ない日本語では約747KBと幅があり、削減量は本文に依存する。条件付き照合や小さな保存応答はAPI拡張として検証し、最新サーバー版・receipt照合や復旧検知を保つ必要がある。

配信JSは非圧縮989,744 bytes。minify後ソースマップからの概算で、CodeMirror系が約51%、React系が約22%。画像やWebフォントの自動取得はなく、アイコンの不要な全件取込も確認されなかった。

- 静的vendor分割は初回の合計を減らさなかった。アプリ部分だけを変える隔離実験ではvendor4ファイルのハッシュが維持され、更新entryは約28KB gzipになった。JS/CSS再利用を導入した後の更新時対策として有効な候補で、初回改善とは区別する。
- GFMの未使用serializer登録を省く試作はgzip9で4,506 bytes（1.4%）削減し、12ケースのAST・HTML計24比較が一致した。効果が小さいため後順位。実装時は下位パッケージの直接依存を明記する。
- minifierのesbuildへの変更は圧縮後も増加し、ES2022指定はサイズが変わらなかった。HTML内の構文解析の削除やエディタの遅延取得には既存の表示・入力準備を変える懸念があり、今回の条件には合わない。

圧縮量の比較は同一条件のローカル計測であり、CDNの実転送量とは分けた。本番への追加の圧縮設定や、有料サービスへの変更はこの調査では必要と判断していない。

調査時の再現用スクリプトは架空データ専用の一時領域で実行し、CIの合否条件には追加していない。測定条件と集計値は [計測証跡](performance-audit-proof.json) に保持する。実装後の機能回帰試験は `e2e/notes-performance.spec.ts`、配信規則の試験は `server/static-cache.test.ts` で管理する。
